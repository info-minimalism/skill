# Release verification

**Official package:** https://github.com/info-minimalism/skill  
**Installed version:** 1.0.0

This package's [release manifest](../release.json) pins its version. An installed copy alone does not prove that it is the latest published version.

## Check the published version

For a latest-version claim, inspect the official repository's current `release.json` through available authorized read access. Confirm that it declares `status: stable`, identifies the Standard version and file, and agrees with the version and status in that Standard. Record the retrieval time and source. If a newer version is present, obtain and read its applicable instructions before evaluating under it, or report that the installed method is outdated. Do not silently substitute a version label.

Use only a stable published version for the every-publication commitment. A prerelease, draft branch, proposed change, installed file timestamp is not the latest published stable version. If the repository or Standard cannot be read, metadata disagree, or no stable release is present, record latest-version verification as unavailable and give only a pinned-version result.

For a historical check, inspect release history or a dated published snapshot showing which version was current at publication. Today's manifest alone does not answer that question. If the history cannot be established, state that limit. Old evaluations keep their original versions.

Reading official release metadata does not authorize installing code, changing configuration, or publishing. If an update needs installation, follow the agent's supported update procedure with the user's authority.

## Local tests

Fixture-supplied release metadata may simulate a stable release solely within an explicitly labeled test. State that it is fixture data, not a live repository observation. Do not use simulated release information in a public evaluation record. Local test results do not establish live publication or publisher adherence.
